# Viva and demo guide

**Use this page to prepare, not to memorise claims.** Every number below can be traced
to `docs/RESULTS.md` or a command in the README. Where something was not measured, the
answer says so.

## 1. One-paragraph pitch

ChallengeMap takes scattered citizen complaints, intercepts duplicates at submission
time, clusters what remains into ranked challenge briefs, and routes each brief to the
universities, NGOs, labs and agencies whose declared capabilities and districts match
it. Every score is stored with its breakdown, so a reader can see why a cluster is
ranked where it is and why a partner was proposed. The demo runs on a seeded synthetic
Jharkhand corpus because no bulk official complaint text is public; the pipeline,
database, API and web client are real and tested.

## 2. Ten-minute demo script

```bash
cp .env.example .env      # set JWT_SECRET and CHALLENGEMAP_BOOTSTRAP_ADMIN
python scripts/dev.py
```

1. **Admin**: sign in with the bootstrap account, open `/admin`, create a partner
   account for `BIT Mesra - Civil Engineering`, and note the org list comes from the API.
The whole path is also scripted and run twice with fresh databases:

```bash
python -m unittest tests.test_lifecycle -v
```

2. **Citizen**: register at `/register` (a different browser/profile), open `/submit`,
   file a water complaint in Ranchi with at least 40 characters.
3. **Duplicate interception**: file the same complaint again; the panel shows the first
   report with a similarity score. Attach it, then open `/reports` to see one report
   `merged` into the other.
4. **Cluster**: back as admin, press **Run cluster job** (needs 8+ pending reports; seed
   a few via `/submit` or `curl`). Drafts appear on the Challenges tab.
5. **Publish and match**: rename a draft, publish it, then confirm or decline the
   proposed partner matches.
6. **Partner**: sign in with the partner account, open `/partners/dashboard`, read the
   score breakdown, and express interest.
7. **Public brief**: open `/challenges`, then the published brief — evidence, district
   counts and monthly timeline come from the reports, not from the demo file.
8. **Methodology**: `/methodology` states what is measured and what is not.

The admin console, OpenAPI docs at `/docs`, and the public pages are the three surfaces
worth showing. There are no screenshots in the repository.

## 3. Questions and honest answers

**Why Jharkhand?**
The project targets a state where grievance counts are published but complaint text is
not, so a text-based discovery layer is genuinely missing rather than duplicative.

**Where is the data from?**
A seeded synthetic corpus generated by this repository (`src/data/synthetic_generator.py`
v1.1.0, seed 42): 15,000 rows, all 24 districts, 12 domains, 71 sub-issues, 1,500
injected duplicates. No real complaint text is included. `docs/DATA.md` records this.

**Is synthetic data acceptable evidence?**
For pipeline development and evaluation mechanics, yes; for claims about Jharkhand, no.
We label every row and every UI surface, and `docs/RESULTS.md` lists the missing real
benchmark rather than estimating it.

**Why didn't you download the CC0 Kaggle benchmark?**
It is the planned real-text check, but it is not in the repository, so it is reported as
not measured. Adding it is the first item under next steps, not a claim we can make now.

**What do the clustering numbers actually say?**
On the mixed-language 3,000-row sample, the best domain partition is TF-IDF char +
Agglomerative at ARI 0.253 / NMI 0.458 / purity 0.442. HDBSCAN and K-Means score lower
(ARI ≈ 0). The English-only slice reaches ARI 0.442, which shows lexical clustering can
separate domains once the script boundary is removed. The low mixed-language score is
explained in `docs/RESULTS.md`: the encoder splits Devanagari from Latin text before it
splits topics. That is exactly the gap a multilingual embedding should close.

**Why keep K-Means in the product if it scores badly?**
The API's re-cluster job needs a fixed, explainable partition and runs on a tiny live
queue; it is not the research result. The measured comparison is in RESULTS, and the
admin can rename or reject any draft.

**How good is duplicate detection?**
Best F1 0.743 at cosine threshold 0.85 (precision 0.742, recall 0.743) over 1,500
injected pairs, using each report's top-5 neighbours in its district. Because that is far
from an oracle, nothing auto-merges: the submitter sees candidates and decides.
`DEDUP_THRESHOLD` defaults to 0.86 in the API, close to the measured optimum.

**Why is dedup blocked by district?**
It matches the measured operating mode and keeps the scan linear. The cost is that the
same real-world problem filed in two districts is not caught; RESULTS lists this.

**Does the supervised classifier prove the domains are learnable?**
It reaches 1.000 on the held-out synthetic set, which is a synthetic ceiling: each
domain has its own vocabulary by construction. It proves the text carries domain signal,
not that real complaints would route perfectly.

**How is priority calculated?**
`0.30·severity + 0.25·log(affected population) + 0.20·volume + 0.15·district spread +
0.10·recurrence`, each component normalised across the groups being scored, then scaled
to 100. The breakdown is stored and rendered. The weights are a documented judgement,
not a validated policy.

**How is partner matching calculated?**
`0.40·tag overlap + 0.25·district proximity + 0.20·severity + 0.15·capacity`, with every
component stored and shown. Proximity is exact-district because no validated centroid
table exists; that simplification is in the code and the UI copy.

**Why SQLite instead of PostgreSQL + pgvector?**
No reachable Postgres instance was available, and faking a migration would be worse than
declaring it. All SQL is behind `api/store.py`, so the swap is local. The costs are real:
no HNSW index (dedup is O(n) per district), no concurrent writers, no managed backups.

**Is authentication defensible?**
Self-hosted JWT access + refresh with rotation and hashed refresh tokens, Argon2id
passwords with an upgrade path from legacy PBKDF2, role checks on every route, and
401-vs-403 tested. Rate limits are per process, which is a gap for multi-worker
deployment. Email verification and password reset are out of scope.

**What about privacy?**
Bulk ingestion strips phone numbers, emails and ID patterns. The API does **not**
automatically scrub submitted text; the form warns citizens and the demo stores only
text you typed. Evidence quotes are shown without usernames. This gap is documented in
`docs/DATA.md` and `docs/ARCHITECTURE.md`.

**Why can a citizen attach to someone else's report?**
Merging only marks their own report and never modifies the target, so cross-account
attachment is what makes duplicate interception useful. The target must exist in the
same district and must not already be merged; ownership of *your* report is enforced.

**What is not implemented?**
Postgres/pgvector, a shared rate-limit store, async jobs, email flows, a verified
24-district GeoJSON/choropleth, charts library, Playwright/Vitest/Lighthouse, the CC0
benchmark, the SBERT comparison, inter-annotator kappa, a manual precision@5 study of
matching, screenshots, the written report and the slide deck.

**What would you do next?**
1. Download and evaluate the CC0 benchmark; 2. install SBERT on 3.12 and run the
TF-IDF-vs-SBERT table; 3. provision Postgres + pgvector and move dedup to HNSW;
4. hand-label 300 rows with two annotators for kappa and precision@5; 5. browser E2E
tests and an accessibility audit; 6. only then the report and slides.

**How was this tested?**
127 Python tests (`-t .` required), a production Next.js build and typecheck, and a
live launcher smoke test (API health 200, web 200, ports released). The UI was not
drive-tested in a browser.

## 4. Claims to avoid

- “Real Jharkhand complaints”, “verified complaints”, “official data”.
- “CC0 benchmark result”, “Sentence-BERT evaluation”, “Cohen's kappa”.
- “Best clustering algorithm is HDBSCAN” — on this corpus it was not.
- “Automatic duplicate merging”.
- “Production-ready”, “scalable”, “secure by default”.
- Any district ranking as “worst”; the UI numbers are demo or local submissions.
